# Rollback plan — Clothing Pilot

Статус: **описан и обоснован на TASK-082**; hosted-репетиция откатов остаётся в
TASK-085.

Этот файл отвечает на один вопрос: что делать, если новый deploy или новая migration
ломает работающий магазин. Восстановление данных описано отдельно в
[RESTORE.md](RESTORE.md).

## Исходные факты, определяющие план

- Цепочка миграций **forward-only**: down-migrations в проекте нет, git-тегов нет.
  Откатить схему «назад одной командой» невозможно by design.
- Push в `main` триггерит Vercel production deployment (D-060 не меняет этого).
  Значит код и схема выпускаются разными механизмами и откатываются по-разному.
- Backup выполняется ежедневно по расписанию `20 1 * * *` UTC. Следовательно
  **RPO — до 24 часов**: при потере базы теряются продажи, внесённые после
  последнего успешного прогона.

RPO в 24 часа **принят Owner** (D-063) как сознательный компромисс для пилота одного
магазина вместо платного плана с point-in-time recovery. При росте оборота решение
пересматривается.

## Случай 1 — плохой deploy, схема не менялась

Самый частый и самый безопасный случай.

1. Откатить deployment в Vercel на предыдущий Ready: promote предыдущего
   production deployment. База не затрагивается.
2. Проверить smoke: `/` → `/login`, вход Owner, открытие Sales и Reports.
3. Только потом разбираться с причиной в отдельной ветке.

Код не «откатывается» через `git revert` в спешке: promote предыдущего deployment
быстрее и не создаёт новых миграций.

## Случай 2 — миграция применена и ломает приложение

Down-migration не существует, поэтому есть ровно два пути.

**Предпочтительный — компенсирующая forward-migration.** Пишется новая миграция,
возвращающая поведение (например, восстанавливающая прежнее определение функции
или policy). Данные сохраняются, история остаётся линейной, ledger не
переписывается.

**Крайний — restore из backup.** Применяется, только если миграция необратимо
повредила данные. Последовательность:

1. Остановить запись: заблокировать доступ Seller через membership status.
2. Восстановить в **отдельный** project по [RESTORE.md](RESTORE.md) и убедиться в
   сверке 43 из 43 таблиц.
3. Только после успешной сверки принимать решение о переключении.
4. Потери данных за период до 24 часов зафиксировать отдельно и внести вручную
   через audited flow, а не правкой ledger.

Restore «поверх» работающего production не выполняется без явного Go/No-Go.

## Случай 3 — потеря Storage при целой базе

`product_images.storage_path` — text-путь, поэтому файлы восстанавливаются
перезаливкой из зеркала архива (шаг 5 в RESTORE.md), без изменения строк в
`public.product_images`.

Обратный случай — база восстановлена, а файлы новее архива — даёт `orphan_rows`.
Сверка из RESTORE.md обязана его показать до открытия магазина.

## Порядок принятия решения

| Кто | Что решает |
|---|---|
| Owner | любой откат production, приём RPO, переключение на восстановленный project |
| Agent | подготовка компенсирующей миграции, restore в изолированное окружение, сверка |

Agent не выполняет откат production и не переключает ресурсы самостоятельно.

## Что ещё не проверено

- Promote предыдущего Vercel deployment ни разу не выполнялся: production не
  существует. Проверяется в TASK-085/TASK-150.
- Компенсирующая миграция не репетировалась на реальном дефекте.
